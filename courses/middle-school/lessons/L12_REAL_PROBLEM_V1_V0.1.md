# 初中 L12 — 一个真实问题，一款小产品 V1 V0.1

更新时间：2026-09-01
状态：CONDITIONAL READY / 当前支持 M1/M2；工具型路径待 M5
年级：7–9年级
标准课时：45分钟
主机制：真实问题缩小 / 产品 V1 / 用户目标
平台：微信小程序教育平台

## 1. 本节课对外成果

每名学生/小组下课前必须有：

> **一个围绕真实校园/学习/兴趣问题的可运行 V1，而不是只停留在讨论问题。**

当前已验证可落地的类型优先：
- 学习工具；
- 知识/兴趣产品；
- 游戏化挑战；
- 信息/推荐产品。

校园记录/管理/工作台类在 M5 Strong Pass 后加入正式菜单。

## 2. 核心观念

教师强调：
> **问题越大，不代表项目越厉害。能做出一个真正工作的解决方案，比喊一个巨大问题更重要。**

## 3. 问题缩小卡

学生只回答四个问题：
1. 谁遇到这个问题？
2. 他在什么场景下最麻烦？
3. 如果产品只能帮一件事，帮什么？
4. 用户做完后，怎样算“解决了一点”？

低能力学生从主题池选择：
- 背单词容易忘；
- 课间不知道玩什么；
- 社团活动信息太散；
- 校园知识难记；
- 想推荐书/电影/运动项目；
- 环保挑战缺少参与感。

## 4. 45分钟时间盒

### 0–6分钟 — 从“大问题”缩成“小任务”
教师把“提高全校学习效率”缩成“帮助七年级学生每天10分钟复习20个词”。

### 6–11分钟 — 完成问题缩小卡
教师重点拦截：
- 用户太泛；
- 同时解决3个以上问题；
- 需要真实学校后台/API才能成立的方案。

### 11–19分钟 — 选择稳定母版并生成 V1
当前优先：M1/M2。

模板：
> 我要给【用户】解决【场景中的小问题】。这个产品最重要的是让用户完成【核心任务】，完成后【成功表现】。请基于一个稳定、可运行的微信小程序骨架直接生成V1，不需要登录、服务器或复杂接口。先只做3个以内核心功能。

### 19–27分钟 — 让 V1 真正符合问题
学生实际使用并检查：
- 这个产品真的对准问题了吗？
- 有没有功能只是看起来厉害、但没帮助？

至少修改一处。

### 27–34分钟 — BASE DEADLINE：形成展示级 V1
到34分钟必须：
- 有明确用户；
- 有核心任务；
- 3个以内核心功能；
- 产品可完整运行；
- 有一处个人/校园内容；
- 可展示。

### 34–40分钟 — 同伴“问题匹配”测试
体验者回答：
> “如果我是这个用户，我觉得它最有帮助的是哪一步？”

作者据此再改或明确不改。

### 40–43分钟 — Challenge
快学生增加第二优先级功能，但必须解释为什么值得。

### 43–45分钟 — 一句话发布
> “我的产品给【用户】解决【小问题】，最重要的是让他【核心任务】。”

## 5. DISPLAY-SAFE BASE
- 真实/具体用户；
- 小而明确的问题；
- 可运行 V1；
- 核心功能不超过3个；
- 一个明显学生决定；
- 可扫码展示。

## 6. FALLBACK
若问题过大：
> 把目标缩成“一个用户在一次使用中只完成一件事”。重新选择 M1/M2 稳定母版，先做出完整 V1。

若项目依赖真实学校数据/API：
> 改为演示版/本地数据版，不接真实系统。

## 7. 教师追问
“我要解决所有学生的问题” → “先选一个最典型用户。”

“我要做校园超级App” → “第一次打开，他最重要要完成哪一件事？”

“需要学校数据库” → “能不能先用本地数据做一个能展示的版本？”

## 8. Challenge
- 第二用户场景；
- 多模式；
- 用户自定义内容；
- 更复杂反馈；
- M5通过后升级为真实记录/管理工具。

## 9. 课后教师最小记录
- V1按时完成率；
- 最常见过大问题；
- 需要真实后台/API的项目比例；
- 最受欢迎真实问题类型；
- 哪些需求值得未来做成 M5 模板；
- 2个“问题小但产品很完整”的案例。
