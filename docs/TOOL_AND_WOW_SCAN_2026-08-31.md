# AI 原生低门槛 Wow 成果与工具扫描

更新时间：2026-08-31
状态：ACTIVE SCAN / FIRST PASS

## 1. 扫描目的

本阶段不是寻找“最强编程工具”，而是寻找：

> **过去需要较高技术门槛，现在可以由零基础学生通过自然语言、简单选择和少量修改快速完成，并且成果明显让家长/老师眼前一亮的 AI 原生创作机制。**

硬约束来自 `AGENTS.md` / `docs/DECISIONS.md`：

- 不回到 Scratch / Python / C++ 式传统编程课；
- 学生和老师都不应依赖较强编程能力；
- 尽量不安装复杂环境、不手敲大量代码、不做复杂 Debug；
- AI 承担复杂技术执行，学生负责想法、表达、判断、选择和迭代；
- 优先可点击、可玩、可输入、会反馈、会对话、可分享的作品；
- 目标体验：技术难度约 2/10，作品观感约 8/10。

当前评价维度：

1. 学生操作难度；
2. 教师救援成本；
3. 首次成功时间；
4. 作品视觉/互动冲击力；
5. 个性化空间；
6. 是否真的“会工作”；
7. 可分享/展示程度；
8. 中国学校网络、账号与设备适配；
9. 未成年人/数据/内容合规；
10. 工具替换和迁移成本。

# 2. 方向 A：一句话生成 HTML 动画、3D 场景、游戏、模拟

## 2.1 这类网上演示到底是什么

很多“新模型对比”中看到的 3D 动画、熟悉电子游戏、物理模拟，并不一定是视频生成模型在逐帧“画视频”。

目前已经存在成熟的公开评测方式：给多个大模型同一个自然语言任务，让模型一次生成一个完整的单文件 `.html` 应用，然后直接在浏览器运行，比较：

- 是否能运行；
- 是否符合场景；
- 动画是否连续；
- 交互是否正常；
- 游戏规则是否完整；
- 视觉是否具体、丰富；
- 模拟/物理行为是否合理。

公开样本包括：

- HTML AI Battle：同一 prompt，一次生成游戏、动画、模拟等单文件 HTML；仓库包含 Super Mario、Snake、physics simulation 等实验；
- Single HTML Game Bench：零迭代，一次生成完整 3D 游戏；
- WebDev Arena / Code Arena：真实用户给需求，模型生成可交互 Web 应用并由用户比较。

来源：

- https://github.com/diegocp01/html_ai_battle
- https://chojondocho.github.io/single-html-game-bench/
- https://arena.ai/blog/webdev-arena
- https://arena.ai/leaderboard/code

核实日期：2026-08-31。

## 2.2 背后技术机制（学生不需要学）

最简单情况下，AI 实际替学生完成了过去程序员需要做的工作：

1. 生成 HTML 页面；
2. 生成 CSS 视觉样式；
3. 生成 JavaScript 交互逻辑；
4. 需要动画时使用浏览器动画循环；
5. 2D 场景可使用 Canvas / SVG；
6. 3D 场景可使用 WebGL / Three.js 等库；
7. 游戏加入键盘/鼠标控制、碰撞、计分、胜负规则；
8. 模拟加入速度、重力、阻尼、碰撞等简化物理规则；
9. 浏览器实时执行代码并渲染每一帧。

因此它与文本生成视频有一个非常重要的区别：

### A. 文本/图片 → 视频模型

AI 直接生成连续视频画面。

优点：画面可以非常逼真。

缺点：通常不能点击、不能玩、不能改变规则；学生对作品的“控制感”和后续可修改性较弱。

### B. 文本 → 可运行 HTML/3D/游戏代码

AI 生成规则和程序，由浏览器实时运行。

优点：可交互、可玩、可继续修改；同一规则下运动具有连续性；非常适合“用自然语言创造一个会工作的东西”。

缺点：高级 3D 画质仍受浏览器、库、模型代码质量影响；复杂物理并不等于真实物理引擎。

对本项目而言，B 类比纯视频更值得优先研究。

## 2.3 为什么看起来像“模型一下子就做出来”

用户输入的可能只是一段自然语言，例如：

> 做一个坐船穿过江南水乡的 3D 场景。船沿河向前，左右是白墙黑瓦的房屋、石桥、树木、灯笼；水面有倒影和波纹，经过桥下时视角自然变化。

模型随后一次性写出数百到数千行 HTML/CSS/JS，用户完全不需要自己理解代码。浏览器承担运行与渲染，因此用户体验上就像“说一句话，场景出现了”。

如果使用 Agent 型工具，Agent 还可能自动：

- 创建文件；
- 启动本地网页；
- 检查报错；
- 根据运行结果继续修；
- 再把结果展示给用户。

因此“用户只做一步”不等于“后台只做了一步”。AI 已经把过去程序员的多步骤执行过程隐藏掉了。

## 2.4 为什么特别适合我们的兴趣课

这是目前最符合“技术难度 2/10、作品观感 8/10”的候选机制之一。

学生可以只做：

> 想法 → 描述 → 看第一版 → 玩/看 → 指出问题 → 要求 AI 修改 → 加入自己的规则/角色/故事 → 展示。

不必把 HTML、JavaScript、Three.js 变成显性教学内容。

### 特别适合制造的第一波惊讶

- “我一句话做出了一个能跑的游戏”；
- “我画的角色进入了游戏”；
- “这个 3D 世界是我描述出来的”；
- “我觉得船太快，于是我让 AI 改慢并增加一座桥，它真的改了”；
- “同学可以直接玩我的版本”。

### 暗线能力

- 把脑中画面说清楚；
- 场景拆解；
- 规则表达；
- 发现 AI 没做对的地方；
- 精确修改；
- 试玩和用户反馈；
- 判断“看起来对”与“真的按规则工作”的差异。

## 2.5 课程化风险

不能因为公开模型 Benchmark 能做，就直接认为课堂稳定。

风险包括：

- 模型偶尔第一次生成失败；
- 外部 Three.js/CDN 在学校网络不可用；
- 一句话生成结果差异过大；
- 复杂 3D 场景对旧电脑性能要求较高；
- 学生一味堆需求导致应用变坏；
- 熟悉游戏的版权角色不能直接用于公开商业展示；
- 如果教师必须看代码才能救场，则违背课程硬约束。

因此正式课程不应采用“完全开放、每个人从空白随便写一个超复杂 3D 游戏”的方式。

更合适的是：

> **AI 原生 + 教师预设稳定底座 + 学生自然语言个性化。**

例如准备 3–5 个稳定的创作底座：平台跳跃、躲避、探索、互动场景、简单模拟。学生通过自然语言改变主题、角色、规则、视觉、关卡和反馈。

# 3. 方向 B：WorkBuddy 式“一句话做出复杂工作台/轻应用”

## 3.1 网上演示看起来为什么这么夸张

腾讯 WorkBuddy 官方定位是全场景 AI Agent 工作台。与普通聊天机器人不同，它可以：

- 理解自然语言任务；
- 自主拆解和规划；
- 读写授权的本地文件；
- 执行终端命令；
- 写并修改代码；
- 在内置浏览器预览网页；
- 继续检查和修正；
- 使用 Skill、MCP、连接器或专家团扩展能力。

官方资料还明确提供：

- HTML 页面生成与预览；
- HTML + CSV 搭建“轻应用”；
- 一键发布 HTML 为在线网站；
- 个人工作台、项目管理看板、记账、任务管理等示例；
- Ardot 对话生成 UI → 修改 → 一键生成应用代码的流程。

来源：

- https://www.workbuddy.cn/docs/workbuddy/Overview
- https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Right-Sidebar
- https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Library/Lightweight-Publish
- https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Design-Idea
- https://www.workbuddy.cn/work/

核实日期：2026-08-31。

## 3.2 很多“复杂桌面工具”可能实际上并不复杂

用户看到的可能是：

- 左侧导航；
- 今日日程；
- 待办；
- 笔记；
- 番茄钟；
- 项目卡片；
- 统计图；
- 学习/工作快捷入口。

视觉上像一个完整“个人操作系统”或桌面软件。

但它完全可以只是：

> **一个浏览器里的 HTML/JavaScript 轻应用。**

数据可以先用：

- 浏览器 localStorage；
- 一张或多张 CSV；
- 简单 JSON；

根本不需要服务器、数据库、用户系统。

这就是 AI 时代一个非常重要的“视觉复杂度 ≠ 技术复杂度”现象。

### 真正连接日历、邮箱、企业系统则不同

如果展示中的“日程”真的读取用户 Outlook/腾讯会议/日历，“待办”真的同步第三方任务系统，那么通常需要：

- API；
- OAuth；
- Connector；
- MCP；
- 权限管理；
- 账号安全。

这会快速提高课程复杂度，不适合第一阶段学生课。

因此我们要借的是：

> **复杂产品的外观与交互体验 + 极轻的数据底座。**

而不是第一天就复制真实办公系统集成。

## 3.3 WorkBuddy “一句话”背后实际做了什么

对用户来说可能只有：

> “帮我做一个个人学习工作台，把课程表、待办、笔记、番茄钟、阅读清单和本周完成情况集成在一起。”

但 Agent 背后可能自动完成：

1. 理解需求；
2. 规划页面结构；
3. 设计 UI；
4. 创建 HTML/CSS/JS 或 React 文件；
5. 写交互逻辑；
6. 创建数据文件；
7. 启动本地预览；
8. 检查错误；
9. 修改；
10. 交付可预览结果。

如果使用 WorkBuddy 专家团，官方还描述了“产品经理定需求、架构师设计和拆任务、工程师实现、QA 验证”的软件开发协作方式。

所以用户的体验是“一句话”，本质上是 AI Agent 替他完成了一次小型软件团队工作流。

## 3.4 对我们课程最有价值的版本

不建议让小学生做“工作管理系统”。

但这个机制可以转化成儿童自己的产品：

### 小学高年级候选

- 我的兴趣基地：收藏、任务、打卡、成就、作品展示；
- 我的宠物研究站：资料卡、观察记录、图鉴、小测验；
- 我的班级活动中心：日历、投票、任务、积分、照片墙；
- 我的英语冒险中心：单词闯关、错题、积分、角色成长；
- 我的旅行指挥中心：地图式路线、打卡、预算、任务、小知识。

### 初中候选

- 我的个人学习驾驶舱；
- 校园社团管理台；
- 个人项目管理工具；
- 阅读/电影/运动数据工作台；
- 模拟创业项目运营台；
- 带简单 AI 问答的兴趣知识应用。

这里的关键不是“功能数量”，而是：

> **学生自己决定这个产品解决什么问题、需要哪些模块、哪些功能好用，并通过自然语言让 AI 改到自己满意。**

## 3.5 为什么很适合第二波能力跃迁

第一波 Wow 可以是：

> “我居然能做一个游戏/动画/3D 世界。”

第二波更高级的惊讶可以是：

> “我居然能做一个别人真的可以用的产品。”

这会把课程从单纯娱乐创作提升到“数字创造者”的身份感。

## 3.6 WorkBuddy 本身是否直接作为课堂工具：暂不下结论

国内 `workbuddy.cn` 的隐私保护声明主要面向成年人，但对未成年人规定了监护人阅读/同意等要求；海外 `workbuddy.ai` 隐私政策则明确写明儿童不得使用服务。不同版本条款存在差异，因此不能直接把海外或国内条款互相替代。

来源：

- https://www.workbuddy.cn/privacy/
- https://www.workbuddy.ai/document/privacy-policy

课程正式选型前必须单独核实：

- 国内学校集体教学是否可用；
- 学生账号如何管理；
- 14 岁以下学生的监护同意/儿童信息处理要求；
- 是否存在学校/企业版统一账号方案；
- 数据是否进入第三方模型；
- 是否可以由教师账号/课堂平台代替学生个人账号。

因此当前结论是：

> **WorkBuddy 是非常重要的“机制参考”和教师/课程研发工具，但是否直接给中小学生使用仍需专项合规与课堂可用性验证。**

# 4. 两个方向横向比较

| 维度 | 单文件 HTML/游戏/3D | WorkBuddy 式轻应用 |
|---|---|---|
| 第一次 Wow | 极强 | 强 |
| 游戏性 | 极强 | 中 |
| “像真正产品” | 强 | 极强 |
| 技术可隐藏程度 | 极高 | 极高 |
| 学生需要懂代码 | 否 | 否 |
| 教师潜在救援难度 | 中 | 中 |
| 45–60 分钟 Demo | 很适合 | 适合（需模板化） |
| 学期课持续扩展 | 强 | 极强 |
| 个性化 | 极强 | 极强 |
| 外部账号/授权风险 | 低到中 | 中到高（若用连接器） |
| 建议优先级 | **P0** | **P0/P1** |

初步产品判断：

1. **单文件 HTML 游戏/动画/互动场景**：优先做 Wow Demo 原型；
2. **轻应用/个人工作台**：优先做“真正有用的产品”原型；
3. 两者都尽量采用“学生不看代码、教师不讲代码”的教学界面；
4. 真正外部服务连接暂时不进入第一轮课；
5. 先证明低门槛高完成率，再逐步增加智能体/AI 对话能力。

# 5. 第一轮候选 Wow 原型池

当前建议至少实测以下 6 个，而不是直接凭讨论确定最终课程：

## P0-A1：一句话生成“江南水乡 3D 航行”

学生描述自己的水乡世界，AI 生成船、河道、桥、房屋、灯笼、树木、天气和镜头运动。

验证重点：

- 是否能 10–20 分钟内看到可运行结果；
- 普通学校电脑帧率；
- 修改一个具体元素是否稳定；
- 是否足够体现学生自己的选择；
- 是否适合全班同时使用。

## P0-A2：一句话生成“我的小游戏”

优先选择结构简单但反馈强的类型：

- 躲避；
- 平台跳跃；
- 追逐；
- 收集；
- 迷宫；
- 简单塔防/防守。

学生重点修改角色、主题、规则、奖励、障碍和关卡，不学习代码。

## P0-A3：我的 AI 宠物/角色

角色可点击、会反馈、有状态；后续可加入对话。

适合小学高年级，并可能向低年级简化。

## P0-B1：我的“学习驾驶舱”

一个页面集成：

- 课程表；
- 待办；
- 番茄钟；
- 目标；
- 成就；
- 笔记/灵感。

第一轮只使用本地数据/浏览器存储，不接真实学校系统。

## P0-B2：兴趣主题“数字基地”

学生任选恐龙、足球、昆虫、动漫、汽车、旅行、音乐等主题，AI 根据学生定义生成一个带资料、收藏、任务、测验、记录和互动的轻应用。

## P1-B3：五年级“英语学习平台”复现型

参考采购方提到的真实惊讶案例，但不照抄具体产品。

验证一个零基础学生能否通过 AI 在一堂或数堂课内完成：

- 单词学习；
- 小测验；
- 积分；
- 错题；
- 简单进度；
- 个性化主题。

重点测试“像真正平台”的效果是否足够强，同时是否避免复杂账号/服务器/数据库。

# 6. 当前明确淘汰/后置方向

第一轮不优先：

- Unity / Unreal / C# 等真实游戏引擎教学；
- 要求学生配置 Node/Python 开发环境；
- 真实数据库、服务器和登录系统；
- OAuth、邮件、日历等复杂外部连接；
- 需要学生读懂代码才能继续修改；
- 单纯生成图片/视频但没有学生交互与迭代；
- 只有教师能成功、学生必须按同一模板照抄的成果。

这些并非永远不用，而是不符合第一阶段“极低技术门槛 + 高成功率 + 高展示冲击”的目标。

# 7. 下一步真实测试计划

研究必须从“网页上看别人能做”进入“我们自己真实跑出来”。

建议顺序：

1. 确认 2–4 个国内可稳定使用的自然语言生成 HTML/应用工具或 Agent；
2. 用完全相同的 3 个 Prompt 测试：3D 水乡、小游戏、学习驾驶舱；
3. 每个工具记录：首次成功时间、步骤数、失败率、修改稳定性、发布方式、账号门槛；
4. 用普通教师视角执行一次，不使用代码级救援；
5. 用“学生只能说需求、选结果、指出问题”的限制再执行一次；
6. 最终筛选 3 个 Wow Demo 原型进入真实试课。

本文件为动态扫描记录。后续每发现一个候选工具/作品机制，应增加事实来源、真实测试记录和判断，不以宣传视频替代实测。
