# AI-Courses 教学资料访问与知识产权保护策略

日期：2026-09-25  
状态：设计草案 / 待合并  
适用：课程方、代理商、授课教师、学校

## 一、核心结论

课程方不应把完整教师手册、完整学生手册、全年 Prompt/模板库、完整故障处理库一次性交给代理商。

但也不能把保护策略简单理解为“教案不发”。

因为只要代理商长期授课，就一定会逐步知道课程内容。真正有效的做法是：

> **把完整课程知识留在课程方系统里，把授课所需信息按身份、按学校、按班级、按课次动态下发；同时把作品、成果、认证、更新和技术支持继续留在课程方体系中。**

目标不是做到“绝对无法复制”，而是做到：

> **脱离课程方之后，代理商只能保留零散课堂经验，而拿不到完整课程系统、最新版本、稳定模板、故障库、作品体系和学校成果交付能力。**

---

# 二、资料分三层，而不是“给 / 不给”两层

## A层：课程方内部资料

只存放在课程方内部，不对代理商长期开放：

- 完整小学 / 初中教师手册；
- 完整学生手册源稿；
- 32节全部课程源文件；
- 全量 Prompt / 母版 / 模板；
- M1–M5 研发底座；
- 全量故障案例与修复路径；
- 课程设计理由；
- 未发布课程；
- 下一版本计划；
- 真实课堂跨校数据；
- 课程迭代规则；
- 代理渠道策略。

这些是课程方的核心研发资产。

## B层：认证教师“授课时可用”资料

教师本人可以通过我们的 Teacher Portal 查看，但不应以完整学期文件形式长期下载：

- 当前课完整教师教案；
- 本节课堂课件；
- 当前学生任务；
- 当前课演示作品；
- 当前课允许的个性化范围；
- 当前课常见问题处理；
- 做得快学生的扩展任务；
- 下课收口；
- 课后记录入口。

建议采用：

> **按教师身份 + 学校 + 班级 + 课次授权。**

正常情况下只开放：

- 当前课；
- 下一课；
- 必要的上一课回顾。

不一次开放完整16课教师手册。

## C层：代理商可长期持有资料

代理商长期持有的应该是“经营和交付组织资料”，不是完整课程配方：

- 对外课程介绍；
- 学期课程主题总览；
- 学校销售材料；
- Demo / 公开课销售脚本；
- 项目实施流程；
- 教师培训安排；
- 学校开课条件；
- 代理商运营手册；
- 授权和班级激活说明；
- 学校成果说明；
- 品牌使用规范。

原则：

> **代理商知道卖什么、怎么组织教学，但不持有完整课程内容库。**

---

# 三、Teacher Portal 应该做什么

不需要重做微信小程序教育平台。

微信小程序教育平台继续承担：

- AI小程序生成；
- 学生实际创作；
- 预览；
- 发布；
- 二维码。

我们自己的系统只做“课程控制层”。

第一版 Teacher Portal 最少需要：

## 1. 身份和授权

- 代理商账号；
- 教师个人账号；
- 学校；
- 班级；
- 授权课程；
- 授权有效期。

教师不能共享统一账号。

## 2. 按课解锁

教师进入后看到：

> 今天上第几课 → 直接打开本课教学页。

本课结束后保留有限回看。

未到课次不默认开放完整内容。

## 3. 单课整合页

不要再让教师打开多个文件。

一节课页面直接整合：

- 老师先看；
- 课前准备；
- 教学流程；
- 课堂投屏；
- 学生任务；
- 常见问题；
- 快学生安排；
- 收口；
- 课后记录。

老师上课只打开这一个页面。

## 4. 动态下发学生任务

学生端只拿到本节需要的：

- 任务；
- 主题选项；
- 当前 Prompt / 操作文本；
- 扩展任务。

不要把整个学期任务册一次性交给代理商。

## 5. 核心内容服务器端保留

尽量不要把：

- 完整母版 Prompt；
- 全量恢复策略；
- 完整课程JSON；
- 后续课内容；

一次性下载到客户端。

只返回当前页面所需内容。

## 6. 身份水印

教师页面、打印件、临时PDF可带：

- 代理商；
- 教师；
- 学校；
- 授权编号；
- 日期。

水印不能防止复制，但能明显提高外传成本和责任可追踪性。

## 7. 作品回收

学生每节作品回到我们的系统登记：

- 学生编号；
- 作品二维码/链接；
- 最佳截图；
- 本节完成状态。

这样真正的课程成果链仍在我们手中。

## 8. 官方成果输出

由我们的系统产生：

- 学生作品集；
- 学期作品轨迹；
- 班级成果页；
- Demo Day页面；
- 学校成果报告；
- 证书 / 徽章。

代理商如果绕开我们，会立即失去这些正式输出。

---

# 四、不要把“完整教师手册”直接给代理商

内部仍然应该制作完整教师手册。

原因：

- 课程研发必须有一份完整单一事实源；
- 培训师需要全局理解；
- 审核和版本控制需要完整手册；
- 课程方自己授课时需要完整材料。

但它的交付方式应当是：

> **内部完整手册 → Teacher Portal 按课渲染 → 教师授课时看到当前内容。**

而不是：

> 完整 PDF / DOCX → 发给代理商 → 永久保存。

---

# 五、学生手册也不要一次性交出去

学生手册同样可以内部完整制作。

但外部建议改成：

### 方式A：平台逐课任务页

最安全，也最适合动态更新。

### 方式B：课堂前生成本节一页纸

由 Teacher Portal 生成：

- 本节任务；
- 本节检查；
- 本节作品记录。

教师可打印，但只包含这一课。

不建议把16课完整学生手册一次发给代理商。

---

# 六、必须考虑课堂断网和平台故障

如果所有内容只能实时访问我们的系统，系统一故障就会导致课堂失败。

因此要做“有限离线兜底”，不是完全禁止下载。

建议：

- 授课前24–72小时开放当前课和下一课；
- 教师可缓存当前课；
- 可以生成当前课的水印应急PDF；
- PDF只含当前一课；
- 不包含完整母版库和后续课程；
- 平台恢复后仍回到在线系统提交作品和课堂记录。

目标：

> **保护IP不能以牺牲课堂可靠性为代价。**

---

# 七、真正的壁垒不能只靠“藏教案”

即使不发完整教师手册，授课教师上过一学期以后仍会知道很多内容。

因此必须把壁垒建立在组合上：

1. **课程内容**：持续更新，而不是卖一次快照；
2. **Teacher Portal**：按课授权与下发；
3. **稳定母版**：不完整外发；
4. **教师认证**：认证归课程方；
5. **班级激活**：正式班级必须在系统激活；
6. **学生作品体系**：作品持续回到课程方；
7. **学校成果报告**：由系统生成；
8. **持续更新**：每学期更新课和平台适配；
9. **技术救援**：最新故障库和恢复方案由课程方维护；
10. **合同和保密**：与技术/运营措施共同存在。

---

# 八、推荐商业结构

不是：

> 一次性卖16节教案。

而是：

> **学期/年度授权 + 认证教师 + 班级激活 + 动态课程下发 + 学生成果系统 + 持续更新。**

代理商的价值是：

- 销售；
- 学校关系；
- 招生；
- 教学组织；
- 本地教师管理。

课程方持续控制：

- 课程；
- 教师授权；
- 教学内容；
- 版本；
- 母版；
- 学生成果；
- 报告；
- 更新。

---

# 九、最小实现建议

第一版不需要建设重型教学平台。

可以先做一个非常轻的课程控制平台：

### 教师登录

教师账号绑定：

- 代理商；
- 学校；
- 班级；
- 课程版本。

### 首页

只显示：

- 本周第几课；
- 上节完成情况；
- 今天开始上课。

### 点击本课

进入单页：

1. 老师先看；
2. 课前准备；
3. 教学流程；
4. 课堂投屏；
5. 学生任务二维码；
6. 常见问题；
7. 快学生任务；
8. 下课收口；
9. 提交课堂记录。

### 学生

扫描本节任务二维码，只看到这一课任务。

学生实际创作仍跳转微信小程序教育平台。

完成后回课程平台提交：

- 作品链接 / 二维码；
- 截图；
- 极简反思。

这已经足以形成第一版控制层。

---

# 十、判断原则

以后凡是设计新的教师交付物，先问：

> **这份资料老师需要在课堂上知道吗？**

如果需要：

> 通过 Teacher Portal 在需要的时间给教师。

如果不需要：

> 留在课程方内部，不发给代理商。

最终目标：

> **老师能轻松上课，代理商能轻松交付，但任何一方都不需要、也不应该长期持有完整课程研发系统。**
